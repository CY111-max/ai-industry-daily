# 采集频率与简报频率改造

日期：2026-09-30
状态：已与用户确认，待实施

## 背景

当前系统每天采集两次（北京 09:00 / 21:00），每个批次生成一份简报。上线 20 天后的实际数据：

- 37 个批次，1354 条资讯（去重后 1196 条唯一），约 60 条/天
- **每个批次都生成了简报**，即每月约 60 份简报 —— 远超实际阅读需要
- `data/` 总量 896K，30 天滚动清理正常

用户要求改为：约 3 天采集一次、一个月写一次简报、简报永久保存。

## 已确认的决策

| 项 | 结论 |
|---|---|
| 简报口径 | **滚动 30 天**：距上一份简报满 30 天就生成一份，覆盖最近 30 天。不做自然月，避免当月空窗 |
| 批次内容 | **只放本次新增**，批次之间不重复 |
| 采集排期 | **每周一、周四 09:00（北京）**，每批三次兜底 |
| 简报展示 | **跟随批次**：切到某批资讯时，显示覆盖该段日期的那份简报 |
| 简报保留 | **永久保存**，不参与清理 |
| 批次保留 | **90 天**（必须 > 30 天，否则生成简报时源数据已被清理） |

## 一、数据模型

### 批次 `data/YYYY-MM-DD-HHmm.json`

保持现有命名（`slot` 恒为 `0900`），减少迁移面。**移除 `briefing` 字段** —— 简报不再挂在批次上。

```json
{
  "id": "2026-10-01-0900",
  "date": "2026-10-01",
  "slot": "0900",
  "slotLabel": "09:00",
  "generation": "morning",
  "updatedAt": "2026-10-01T01:12:00.000Z",
  "items": [
    { "id": "url-md5", "title": "…", "source": "…", "time": "…", "url": "…", "digest": "…" }
  ]
}
```

`items` **只含本次新增**，不含历史结转。

### 简报 `data/briefings/YYYY-MM-DD.json`

新建子目录。文件名用生成日期。**不参与任何清理**。

```json
{
  "id": "2026-10-02",
  "from": "2026-09-02",
  "to": "2026-10-02",
  "generatedAt": "2026-10-02T01:20:00.000Z",
  "itemCount": 1794,
  "batchCount": 9,
  "briefing": {
    "summary": "…",
    "part1": { "launch": [], "line": [], "risk": [], "policy": [] },
    "part2": { "finance": [], "capital": [], "chain": [], "corp": [] }
  }
}
```

`briefing` 内部结构与现有 `normalizeBriefing` 输出完全一致，前端渲染代码无需改动。

### 索引 `data/index.json`

在现有 `batches` / `dates` / `latest` 基础上增加 `briefings` 数组，前端一次请求拿全，不必多发一个请求：

```json
{
  "batches": [ { "id", "date", "slot", "generation", "count", "updatedAt" } ],
  "briefings": [ { "id", "from", "to", "itemCount", "batchCount", "generatedAt" } ],
  "dates": [],
  "latest": "2026-10-01-0900",
  "updatedAt": "…"
}
```

`briefings` 按 `to` 倒序（最新在前）。

## 二、采集流程

每周一、周四北京时间 09:00 采集，每批三次兜底（06:40 / 07:40 / 08:40，对应 UTC 22:40 / 23:40 / 00:40）。

```
抓取 7 个源
  → 相关性过滤
  → 去重（窗口 7 天 → 14 天）
  → 补详情
  → AI 摘要（只对本次新增）
  → 追加写入本批次文件
  → 判断是否需要生成简报
  → 更新索引
  → 清理超期批次
```

**去重窗口放宽到 14 天**：现在漏跑一次就是 6 天空窗，7 天窗口在连续两次失败时会漏收。14 天覆盖两轮失败仍有富余。

**同批次重复运行**（兜底的第 2、3 次）：以本批次文件为底稿，只追加真正新增的条目；已有摘要的不重复调用大模型；本轮无新增则**不改写文件**，避免空提交。

**跨午夜延迟**：批次日期由运行时北京时间决定。延迟超过 17 小时才可能跨过午夜把日期记错（实测最长 6 小时），不额外处理。

## 三、简报生成

### 为什么必须两级汇总

30 天约 1800 条唯一资讯。现有实现是把全部条目（标题+来源+摘要+日期，约 130 字符/条）塞进单次调用，合计约 23 万字符，**远超 DeepSeek 的上下文上限**，直接调用必然失败。

### 两级结构

**一级（分块）**：以「批次」为分块单位（每块约 180 条）。每块用现有 `BRIEFING_SYSTEM` 提示词生成一份阶段小结，输出仍是两板块八小节结构。约 9 次调用。

选择「批次」而非按条数硬切的原因：批次本身就是自然的语义单元（约 3 天的连续资讯），且无需引入额外的切分逻辑。

**二级（汇总）**：把 9 份阶段小结（每份约 2500 字符，合计约 2.3 万字符 ≈ 1.5 万 token）喂给同一条提示词，产出最终月度简报。1 次调用。

一级产物**不落盘**，只用于二级输入。

### 触发条件

运行时检查：仓库中不存在任何简报，**或** 距最新一份简报的 `generatedAt` 已达 30 天 → 生成一份新的，覆盖 `[now-30d, now]`。

汇总的输入是**所有 `date` 落在覆盖区间内的批次**的全部 `items`，**必须按 `id` 去重**：改造前遗留的批次之间是重叠快照关系（实测跨批重复 1.13x），不去重会重复计数。

### 边界

- 覆盖区间内没有任何批次 → 跳过，不生成空简报
- 区间内只有 1 个批次 → 直接采用一级产物，跳过二级调用

## 四、前端（外观不变）

只改简报模块的数据来源，词云、资讯列表、批次切换**一行不动**。

**简报匹配规则**：切到日期为 `D` 的批次时，取满足 `to > D` 的**最早**一份简报（即"生成于 D 之后、且覆盖到 D"的那份）。

例：批次 9/15，简报有 `B1(to=9/2)`、`B2(to=10/2)` → 命中 B2（覆盖 9/2~10/2，含 9/15）。

边界为什么是**严格大于**：简报的 id 就是它的生成日，`to` 也等于生成日。所以 `to == D` 意味着这份简报是在批次当天生成的 —— 它属于以 `D` 为起点的下一个周期（下一份的 `from` 正好等于这一份的 `to`）。
例：批次 9/2，同上两份简报 → 命中 B2（覆盖 9/2~10/2），而不是 B1。两份都覆盖 9/2，但 B2 是更新的那份。

若没有任何简报满足 `to > D`（批次比所有简报都新）→ 退回**最新一份**。此时显示的简报比批次旧，属于正常情况。

**简报卡片**顶部增加一行小字标出覆盖区间与条数：`覆盖 8/3 ~ 9/2 · 共 1533 条资讯`。用户始终知道自己在看哪一份。

**空态**：没有匹配到简报时显示「当时尚未生成简报」。

不新增按钮。切换批次就是浏览历期简报的方式。

## 五、排期与清理

### workflow crons（UTC）

| cron | 北京 | 批次 |
|---|---|---|
| `40 22 * * 0,3` | 周一/周四 06:40 | 0900 |
| `40 23 * * 0,3` | 周一/周四 07:40 | 0900 |
| `40 0 * * 1,4` | 周一/周四 08:40 | 0900 |

星期字段注意：UTC 的周日/周三 22:40 对应北京的周一/周四 06:40，所以前两条用 `0,3`，第三条用 `1,4`。

**全部映射到 `--slot=0900`**：现在一个采集日只有一个批次，`slot` 仅用于保持文件命名兼容。批次由「哪个 cron 触发」决定，不由运行时刻推断。保留这一机制的原因：实测排期延迟 1.5~6 小时，用墙上时间推断会把批次归错日期。

兜底次数保持 3 次（与用户确认的一致）：实测最坏延迟 6 小时，三次尝试即使全部被推迟，仍落在同一个北京日内，不会跨日错记。

### 清理

只删 `data/` 下超过 **90 天**的批次文件。`data/briefings/` 子目录的目录名不匹配批次文件名规则 `^(\d{4}-\d{2}-\d{2})(?:-(\d{4}))?\.json$`，天然不会被扫描到。

## 六、改造前遗留数据的处理

- `data/` 下 37 个既有批次（09-10 ~ 09-30）保留原样，其中内嵌的 `briefing` 字段被忽略不再读取
- 两个旧格式单文件（`2026-09-10.json` / `2026-09-11.json`，无 slot）继续兼容显示为「全天」
- 改造后**首次运行**因仓库中无简报，会立即生成一份覆盖最近 30 天的简报。此区间既有批次是重叠快照，按 id 去重后约 1196 条

## 八、验证方式

1. `node collector/run.js --dry-run --date=2026-10-01 --slot=0900` —— 批次文件只含新增，无 `briefing` 字段
2. 同批次重复运行 → 文件字节不变，无空提交
3. 删除 `data/briefings/` 后跑一次带 key 的完整流程 → 生成一份简报，`itemCount` 与去重后的窗口条目数一致
4. 本地起 `serve.js`，用 CDP 在 390px 视口验证：
   - 切批次时简报随之切换，覆盖区间标签正确
   - 切到早于所有简报的批次 → 退回最新一份

5. 清理逻辑：造一个 91 天前的批次文件 → 被删除；`briefings/` 下的文件不受影响
